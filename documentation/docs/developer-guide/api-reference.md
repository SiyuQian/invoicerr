# API Reference

Invoicerr's backend exposes a fully documented REST API via [Swagger/OpenAPI](https://swagger.io/), generated from `@nestjs/swagger` decorators on every controller in `backend/src/modules/`.

## Published Specification

The OpenAPI document for the latest build on `main` is published alongside this site, so you can browse or import it without running your own instance or enabling Swagger in production (see [Your Own Instance](#your-own-instance) below):

- **Raw OpenAPI spec (JSON)**: [docs.invoicerr.app/openapi.json](https://docs.invoicerr.app/openapi.json) — import this into Postman, Insomnia, a code generator, or any other OpenAPI-aware tool.

  (Linked as an absolute URL rather than a relative one deliberately: the file is a build-time artifact copied into `static/` by CI, never committed to this repository — see that step's own comment in `.github/workflows/docs-deploy.yml` — so it does not exist for Docusaurus's broken-link checker to verify in a local checkout or a PR preview build that hasn't run that step.)

It is generated by `npm run openapi:dump` (`backend/src/openapi-dump.ts`) — the exact same `DocumentBuilder` configuration and controller metadata `/api/docs-json` serves on a running instance (`backend/src/swagger-document.ts`, shared by both) — and copied into this site's `static/` directory as part of the documentation build (`.github/workflows/docs-deploy.yml`). This is also the interoperability reference the [Terms of Service](../legal/terms-of-service.md), Section 10, points to for the EU Data Act's Article 26/30 disclosure.

## Your Own Instance

Rather than duplicating the reference here, use the live, always-up-to-date Swagger UI served by your own Invoicerr instance:

- **Interactive UI**: `https://<your-instance>/api/docs`
- **Raw OpenAPI spec (JSON)**: `https://<your-instance>/api/docs-json`

For a local development setup (see [Local Development](./local-development.md)), this is typically:

- `http://localhost:3000/api/docs`
- `http://localhost:3000/api/docs-json`

Swagger is served by default outside production. **In production it is disabled unless `SWAGGER_BASIC_AUTH_USER` and `SWAGGER_BASIC_AUTH_PASSWORD` are both set** (`backend/src/main.ts`), in which case it is mounted behind HTTP Basic Auth for every `/api/docs*` path. The published spec above covers exactly this gap for a hosted or otherwise Swagger-disabled instance.

## Authentication

Most endpoints require either a session cookie (browser login) or an API key. See [Authentication](authentication.md) for details on both mechanisms, and the `api-keys` module for managing keys from the UI.

## Reconciliation edit target reads

Use `GET /api/project-reconciliation/projects/:id?caseId=...` to refresh one exact case outside the current page, or `GET /api/project-reconciliation/projects/:id/receipts?receiptId=...` for one receipt. Each returns its existing page shape with one item, or 404 for a missing/foreign project target. These selectors cannot be combined with cursor. Case selection leaves root financial/review measures and the aggregate version global; receipt allocation capacities also remain global. A missing edit target must not become a create operation. Refresh authoritative project detail before refreshing a receipt for an edit decision.

## Historical project reconciliation import

The administrative import workflow uses `POST /api/project-reconciliation/projects/:id/import/preview` and `/import/confirm`. OWNER/ADMIN access and the module write scope are required; API keys also need read-equivalent access to invoices, credit notes, expenses and received invoices. Preview writes nothing. Existing member GET access is unchanged.

Preview accepts exactly `{payload, selectedMatches}`. The Ledgerly payload declares its known currency and sourceAsOf; rows include optional nullable source projectId, which must match the selected source project when supplied. Missing or blank project membership remains blocking. When preparing saved detail/list exports, join by their exact raw source row IDs to supply projectId, move only customerCard/shareCard/lineItems/calculation into the bounded sourceSnapshot, and omit other export fields such as primaryAction. Never supply credentials, source URLs or attachments. No Ledgerly request is made by these endpoints or ordinary project reads.

`selectedMatches` contains `{sourceId, documentId, typeId, caseSourceId}` entries. Both source IDs are historical raw Ledgerly IDs: caseSourceId identifies the customer anchor; documentId is an explicitly chosen existing company document. Exact contextual source invoice numbers discover candidates only; nothing links automatically. Ledgerly linkedInvoiceNumber refers to the paired **other Ledgerly customer/share row**, not an Invoicerr ID. Ambiguous or unpaired shares remain blocking. Amount/name similarity never identifies a document. Every selection must pass company, document type, role, recipient and currency checks.

Preview returns previewHash, sourceHash, projectVersion, sourceAsOf, proposedCases, proposedReferences, proposedLinks, unresolved, errors and counts. Existing/proposed values and snapshot hashes identify blocking REVISION items. Every mapped own-link proposal additionally exposes required `historical: ExternalInvoiceInput` facts beside `candidates[].financial`, including COMPANY customer amounts/status/dates; these are historical comparisons, not another external COMPANY reference. Nonblocking missing own links permit valid case/reference/agreement import, leaving the required-link exception open. Missing dates stay unknown. Paid labels and paidDate create no receipt or payment. Explicit internal-share totals become proposed agreement amounts; sharePercent is never applied. Primary gross must equal its explicit net plus GST. Source cents mean hundredths of the declared currency; conversion to its minor-unit exponent must be exact, without rounding, FX or tax inference.

Confirm sends the identical payload and selectedMatches plus previewHash, requestKey and expectedVersion (the preview's projectVersion string). Editing a match or source input requires another preview. First confirm returns201 and exact retry returns200 with `{result, versionToken, changed:false}`; successful new operations use the same single envelope with changed:true. Retain the entire attempted input/key for transient retries. Changed input under the same key conflicts. Current project, party, candidate membership, document, payment or credit changes invalidate the preview with409 IMPORT_PREVIEW_STALE and zero writes. Refresh and review before submitting a new attempt.

Identity is company/sourceSystem='ledgerly'/raw row ID; moving source rows between projects does not mint new identities. Repeat imports reuse IDs and preserve owner edits. Meaningful changed source facts are blocking revisions; resolve them explicitly through existing case/reference forms before previewing again. Unchanged normalized source facts, or already matching current editable facts, can be reused only with the original share identities. Introducing or rebinding a raw share ID on an existing imported case is a blocking revision even when the current agreement matches; immutable snapshots are not extended through REUSE. Observation-only sourceAsOf changes also reuse existing records: their original snapshots/as-of remain intact, while the new request source hash/as-of is recorded in the root audit. This does **not** refresh historical records or claim the old snapshot reflects a new observation. No pending revision or automatic overwrite operation exists.

Input is rejected whole above 1000 invoice rows (both kinds), 1000 selections or 2 MiB of UTF-8 JSON for the original parsed request before trimming. Each sourceSnapshot is at most 64 KiB UTF-8 with at most 1000 line items and only the documented inert fields. Only POSTs to the two import routes receive a 2 MiB JSON transport limit; other JSON paths/methods retain 1 MiB, URL-encoded bodies retain 64 KiB, and the auth subtree keeps its own stream. Oversized transport bodies return 413 before controller execution; the original parsed-body/snapshot validators also enforce their limits without partial import. Before recomputation, import locks one sorted union of candidate/linked documents and all existing company credit notes, protecting note status and mutable invoice membership; new note inserts serialize through the company FK. All accepted case/reference/link changes and one root audit commit atomically; no canonical invoice, expense, payment, credit, external receipt, reminder, export or outgoing queue is created or changed.
